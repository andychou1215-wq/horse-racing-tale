# 賽馬模擬遊戲 — 數值引擎（MVP 第1步）

依照 `docs/MVP範圍.md` 的建議開發順序，這是第一步：把訓練公式、比賽公式、
六階段位置值計算寫成純邏輯層（無 UI），並用 `數值平衡試算.xlsx` 的公式與
測試馬數據做單元測試，確保程式算出的結果跟試算表一致。

## 結構

```
racing-sim/
  engine/
    constants.py   # 對照表：狀態倍率、適性倍率、跑法階段倍率、體力消耗基準值
    training.py    # 訓練成長公式（培育/培育系統.md）
    race.py        # 比賽六階段模擬（比賽/比賽公式.md、比賽模擬.md、體力系統.md）
  tests/
    test_training.py   # vs 訓練成長模擬 分頁，逐週比對
    test_race.py        # vs 比賽模擬 分頁，8匹測試馬逐階段比對
  data/
    reference_horses.json   # 從 xlsx 匯出的測試馬與預期結果，測試用基準值
  tools/
    regen_reference.py      # xlsx 更新後，重新產生 reference_horses.json
```

## 已實作範圍

- **訓練成長公式**：`成長量 = 基礎訓練值 × 潛力餘裕 × 年齡成長倍率 × 訓練師 × 設施 × 狀態`，
  潛力餘裕機制讓成長隨接近潛力上限而自然趨緩。
- **比賽六階段模擬**：起跑/前段/中段/後段/彎道/衝刺的基礎分數公式、外部乘數
  （騎師修正×距離適性×場地適性×狀態倍率×負磅修正×特性×戰術波動×隨機波動）、
  跑法階段倍率、位置值（六階段相對表現的累積平均，非複利連乘）、最終名次。
- **體力系統**：耐力修正、跑法修正，逐階段體力消耗與剩餘體力。

## 執行測試

```bash
pip install -r requirements.txt
pytest tests/ -v
```

目前 22 個測試全數通過，逐匹馬、逐階段跟 `數值平衡試算.xlsx` 的計算結果比對到
浮點數精度（`rel=1e-6` ~ `1e-9`）。

## 除錯過程中發現的一個對齊細節

比賽公式.md 文字描述「後段基礎階段表現分數 = 耐力×0.5 + 根性×0.2 + 剩餘體力×0.3」
沒有寫明是「進入後段前」還是「後段結束後」的剩餘體力。跟 xlsx 公式核對後，
試算表實際引用的是**後段結束後**（扣除後段自身體力消耗後）的剩餘體力值，
本次實作依此對齊，未更動任何 docs 內容或規則本身，僅在程式碼註解中記錄
這個從公式反推出的實作細節，供之後若要回頭把 `比賽公式.md` 的文字敘述寫得
更明確時參考。

## 第2步：最小可玩 CLI 原型（`cli/`）

依 `docs/MVP範圍.md`「MVP遊戲流程(精簡版)」實作的互動式文字介面，串接
`engine/` 的訓練與比賽引擎，跑完整的「訓練→比賽→成長→再訓練」核心迴圈：

```
cli/
  horses.py       # 5匹開局固定測試馬、可訓練屬性清單
  assumptions.py  # MVP原型專用假設值(訓練師/設施固定倍率、疲勞/財務數字等)
  opponents.py    # NPC假對手馬產生器(依賽事分級中樞屬性隨機生成)
  game.py         # 核心邏輯：訓練/休息/比賽日/週結算，全部呼叫 engine/ 公式
  play.py         # 互動式文字介面
```

執行：

```bash
cd racing-sim
python3 -m cli.play                 # 互動模式，預設玩16週，逐匹馬手動選訓練/報名
python3 -m cli.play --weeks 12      # 指定週數
python3 -m cli.play --auto          # 自動demo模式，亂數代打，用來快速看完整流程
```

### 對應 MVP範圍.md 的取捨

- **保留**：11項屬性訓練成長、六階段比賽模擬與純文字結算、狀態/疲勞、基礎財務
  （固定週支出+報名費+獎金-人員分成）、逐週核心迴圈、每4週一次比賽日。
- **簡化**：僅3級賽事(新馬賽/地方一般賽/GI，用整體評級門檻篩選可報名分級)、
  訓練師/設施固定倍率(不開放升級)、每匹馬固定配一名亂數生成的NPC騎師、
  單一場地(不做天氣/場地狀況變動)、隨機事件僅「幸運訓練/疲勞加劇」兩項。
- **先跳過**：拍賣/市場、繁殖/遺傳、NPC馬主完整決策邏輯(用亂數假對手馬代替)、
  馬主聯盟、特性/個性系統、年度獎項。

`cli/assumptions.py` 內所有假設值(疲勞增減量、訓練/馬房費用、獎金表等)都是
為了讓原型能跑起來先取的具體數字，不是設計定案，之後 play-test 後應該回頭
調整（呼應 GDD 第12節「開放的設計取捨」）。

### 平衡調整記錄（使用者實際遊玩16週後回饋「還蠻好玩的」，接著做的第一輪調整）

- **GI 報名門檻**：原本整體評級75，開局評級76.4的「全能強馬」第一週就報得了GI，
  跳過「先在低階賽事累積成績、練到接近潛力上限才挑戰最高階賽事」的進程感。
  調高到85後，5匹開局測試馬沒有一匹能立刻報名GI(見 `test_no_starter_horse_qualifies_for_gi_at_game_start`)，
  地方一般賽門檻也從55微調到58。
- **疲勞系統**：原本8個訓練選項裡只有1個是休息，導致疲勞值單向累積、很快頂到100
  不再變動。調整為：訓練疲勞增量15→12、休息回復量25→30(休息要更有感，值得選)、
  並新增「每週被動回復5點」(不論本週訓練或休息都會回，代表訓練之外的日常靜養)。
  重新用 `--auto` 模式跑16週驗證：疲勞值會自然上下浮動，不再卡死在100。
- **補上 `cli/` 單元測試**(`tests/test_game.py`，8個)：涵蓋賽事資格門檻、疲勞增減
  方向、被動回復、訓練/休息的簿記正確性、破產判定，測試總數從23增加到31。

### 平衡調整記錄（第二輪：使用者指出「16週來看GI門檻可能過高，但更長模擬也許能解決」）

實際跑模擬驗證後發現：**不是模擬時間不夠長，而是原本的門檻在目前實作下幾乎不可能
達到**。MVP只開放7項屬性可訓練(智力/彎道/精神/健康永遠停在起始值)，用「每週訓練
最低屬性、完全不休息」的理想化模擬，300~500週(將近6~10年，已超過馬匹合理參賽
生涯)才勉強讓潛力上限88的馬摸到85附近，「平衡中庸馬」(潛力上限78)則永遠到不了。

依此做了兩項調整：

- **GI 門檻 85 → 80**。
- **新增「比賽經驗成長」機制**(`apply_race_experience_growth`，使用者決定新增)：
  出賽本身(不論名次)也會對7項可訓練屬性套用一次小幅成長，基礎值依分級遞增
  (新馬賽0.4 / 地方一般賽0.7 / GI1.3)，跟週間訓練同一套潛力餘裕公式，只是基礎值
  低很多，讓「多出賽也是一種歷練」有數值上的意義。

用「每週訓練最低屬性+每4週比賽賺經驗」重新模擬驗證：全能強馬97週、耐力追込馬228週、
速度型快馬341週可達GI門檻，落在馬匹合理參賽生涯內；平衡中庸馬(潛力上限78)維持永遠
到不了，符合「不是每匹馬都是GI等級」的設計意圖。

但發現新問題：**潛力新星潛力上限92(全場最高)，卻是唯一在600週內都碰不到GI門檻的
馬**——因為牠4項凍結屬性起始值太低(智力40/彎道40/精神46/健康55)，拖累「11項屬性
平均」評級，跟「潛力最高」的設定矛盾。依使用者決定，調高這4項起始值(智力58/彎道60/
精神62/健康70)，重新模擬後 458週可達GI門檻——雖然仍偏晚(接近「持久型」成長曲線
8歲引退的上限)，但至少從「永遠到不了」變成「摸得到」，且使用者已決定未來要正式把
智力/彎道納入可訓練屬性(目前 MVP範圍.md 明訂先跳過)，屆時評級天花板會直接等於
潛力上限，這個問題會徹底解決。

補上4個對應測試(GI門檻可達性、比賽經驗成長方向性)，測試總數31→34。

### 第三輪調整：智力、彎道正式開放訓練（徹底解決潛力新星問題）

依上一輪記錄的「未來規劃」，把 `TRAINABLE_STATS` 從7項擴充到9項(新增智力、彎道)，
只剩精神/健康2項維持凍結(目前MVP還沒有對應的訓練管道)。重新用「每週練最弱屬性+
每4週比賽」模擬驗證，達GI門檻(80)所需週數：

| 馬匹 | 潛力上限 | 舊(7項可訓練) | 新(9項可訓練) |
|---|---|---|---|
| 全能強馬 | 88 | 97週 | 72週 |
| 耐力追込馬 | 91 | 228週 | 144週 |
| 速度型快馬 | 93 | 341週 | 152週 |
| 潛力新星 | 92 | 458週(靠調高凍結屬性硬湊) | **272週** |
| 平衡中庸馬 | 78 | 到不了 | 到不了(符合預期) |

潛力新星從「458週勉強摸到」進步到「272週」，且不再需要靠人工調高起始值這種治標
做法——現在牠評級的天花板直接等於潛力上限92，跟其他馬一致，「潛力最高」的設定終於
名副其實。4匹有潛力衝GI的馬都落在合理參賽生涯(最長152~272週，約3~5.2年)內，只有
「平衡中庸馬」(潛力上限78本身就低於門檻)維持進不去，符合賽事分級「不是每匹馬都是
GI等級」的設計意圖。

### 財務長週期驗證（比照 數值平衡試算.xlsx「財務系統進階」分頁的驗證方法）

用 `tools/financial_simulation.py`（疲勞>70就休息、否則練最弱屬性、有資格就報名可報的
最高分級比賽，跑N次獨立試驗取平均）實際驗證財務數字：

```bash
python3 tools/financial_simulation.py --weeks 52 --trials 20
python3 tools/financial_simulation.py --weeks 104 --trials 15
```

- 52週、20次試驗：平均最終資金148,170，最低點101,400，**0次破產**。
- 104週(2年)、15次試驗：平均最終資金131,960，**仍0次破產**。
- 更極端情境(完全不出賽，只算訓練費+馬房費)：52週後150,000→74,650，離破產門檻
  (-20,000)還很遠。

對照 `數值平衡試算.xlsx` 原本困難難度的發現(5匹馬小馬房、沒有明星馬支撐，52週後
從150,000掉到只剩4,650，接近破產)，目前CLI的財務數字大概只有那個緊張感的
1/15~1/20——`TRAINING_COST_PER_SESSION`(150)、`STABLE_WEEKLY_COST`(800)明顯偏低，
撐不出「困難模式」該有的破產壓力。

**依使用者決定**：先維持現狀，不是現在就調整。理由是MVP這個階段的固定支出項目還不
完整(訓練師/獸醫費用、設施升級費用等 MVP範圍.md 先跳過的系統之後補回來時，也會
增加支出)，等這些之後真的補上、財務緊張感如果還是不夠，再一起回頭調整比較有效率，
不用現在為了湊数字先調一次、之後加了新支出又要重調一次。

### 已知可再打磨的地方（下一輪可以繼續調整）

- 精神、健康2項屬性目前仍是凍結屬性，MVP還沒有對應的訓練管道(對應docs的醫療/模擬賽
  系統，MVP範圍.md先跳過)；如果之後也想開放，需要先決定這兩項的訓練方式與效果。
- 財務緊張感偏低(見上方「財務長週期驗證」)，待訓練師/獸醫/設施等支出項目補齊後，
  用 `tools/financial_simulation.py` 重新驗證，再決定是否需要調高固定支出或降低
  比賽收入比例。
- 目前的手感驗證依據是使用者遊玩回饋 + 這裡的理想化模擬(不休息、不受傷)，跟真實
  遊玩(要休息、疲勞限制、隨機事件)之間仍有落差，理想化模擬的週數只能當「下限
  參考」，實際所需週數會更長。

## 第4步：網頁UI（`webapp/`）

把 CLI (`cli/game.py`) 包一層 Flask 網頁介面，**沒有重寫任何遊戲規則**——所有
訓練/比賽/財務計算依然呼叫既有的 `cli.game` / `engine` 函式，`webapp/` 只負責
「畫面」：把表單輸入轉成既有 function 呼叫，把回傳的文字結果轉成網頁呈現。

```
webapp/
  app.py             # Flask 路由：dashboard / submit_week / race_entry / submit_race / new_game
  templates/
    layout.html      # 共用版型(頂部資金列、重新開局按鈕、訊息列)
    dashboard.html   # 馬房總覽 + 本週訓練分配表單
    race_entry.html  # 比賽週的報名+戰術選擇表單
    bankrupt.html    # 破產畫面
```

執行：

```bash
cd racing-sim
pip install -r requirements.txt
python3 -m webapp.app
# 瀏覽器開啟 http://127.0.0.1:5000
```

### 網頁版的遊戲流程

1. **馬房總覽頁**(`/`)：顯示週次、資金、5匹馬的評級/潛力/疲勞/狀態/名氣/累積獎金，
   以及本週訓練分配表單(每匹馬一個下拉選單：休息或9項可訓練屬性之一)。
2. 送出後：非比賽週直接結算(疲勞/成長/固定支出)，顯示結果訊息列，回到總覽頁、
   週次+1。比賽週則導向**報名頁**(`/race_entry`)，列出每匹馬符合資格的分級選單
   +戰術選單(可以都不報名)。
3. 送出報名後：跑比賽、結算獎金/名氣/比賽經驗成長/固定支出，顯示結果訊息列，
   回到總覽頁、週次+1。
4. 資金跌破破產門檻時導向**破產頁**，可以按「重新開局」重來。

### 已知限制

- **單一全域遊戲狀態**：`app.py` 用一個模組全域變數存 `GameState`，不是多使用者/
  多分頁安全設計——這是本機單人開發伺服器的原型做法。2026/8/25使用者決定：這個遊戲
  就定位成單人遊戲，不考慮多使用者/多分頁同時連線的情境，所以這個「限制」其實是
  刻意維持的設計，不是待補的缺口，不用改成資料庫/Flask session那種每個使用者各自
  狀態的架構。
- 沒有做美術/RWD，純功能性排版，符合 UI流程與遊戲迴圈.md「比賽呈現形式：純文字
  結算」的定案，但排版本身還很陽春，之後可以再美化。
- 補上4個路由層的煙霧測試(`tests/test_webapp.py`)，只驗證路由串接正確(能顯示、
  能送出、比賽週會正確導向、破產/重開局正常)，不重測遊戲規則本身(那是
  engine/cli 既有37個測試的責任)。測試總數34→38。

實際在瀏覽器玩過一輪後使用者確認沒問題(第4步驗證通過)，額外加了一個小改動：
`race_entry.html` 依使用者回饋新增疲勞值與狀態欄位，方便報名前直接判斷馬匹狀況。

## 第5步：訓練師系統（`cli/trainers.py`）

財務長週期驗證那輪(見上方)發現破產風險遠低於原設計意圖，使用者當時的決定是
「先維持原狀，等補進新支出項目後財務緊張感仍不夠再調整」。訓練師/獸醫員工
系統正是 MVP範圍.md「先跳過」清單裡那個缺口，所以列為下一步優先項目，使用者
確認後開始實作。

依 `docs/培育/訓練師系統.md`，7種專長先實作4種：

- **速度訓練 / 耐力訓練 / 戰術訓練**：對應可訓練屬性的訓練加成，Lv1~5，
  每級+8%(`training_multiplier`)。
- **狀態管理**：額外提供每週被動疲勞回復加成，每級+1點(`fatigue_relief_bonus`)。
- 先跳過：**幼駒培育**(MVP馬匹全程視為「上升期」不跨成長階段，目前沒有意義)、
  **傷病預防**(MVP還沒有傷病系統)、**潛力評估**(純資訊類，不影響數值，先跳過
  UI呈現差異)。

```
cli/
  trainers.py   # Trainer dataclass、市場生成、專長加成/容量折扣的純函式
```

聘用/指定規則：

- 訓練師市場隨機生成4名可聘用訓練師，聘用要付一次性聘用費，之後每週固定支付
  薪水(併入 `weekly_upkeep` 的固定支出)。
- 一個馬匹最多指定一個訓練師，一個訓練師最佳管理8匹馬；9~12匹時訓練效率打
  8.5折(`capacity_multiplier`)；13匹以上無法再指定。
- 沒有指定訓練師的馬，訓練倍率維持1.0——等同這個系統補回前的固定假設值，
  向下相容，不會讓沒管理訓練師的玩家吃虧，只是少了加成。

`cli/game.py` 的變動：`train_horse()` 簽名改吃 `GameState`(內部查詢指定訓練師
換算實際倍率)，新增 `hire_trainer()` / `assign_trainer()` /
`trainer_effective_multiplier()`。比賽經驗成長(`apply_race_experience_growth`)
刻意不吃訓練師加成——那代表馬匹自身出賽歷練，不是訓練師在場邊指導。
`assumptions.py` 移除原本的 `FIXED_TRAINER_MULTIPLIER` 固定假設值。

網頁版新增 `/trainers` 頁面：訓練師市場列表+聘用按鈕、已聘用清單(含目前管理
馬匹數)、逐匹馬指定訓練師的表單；`dashboard.html` 新增「訓練師」欄位顯示每匹
馬目前指定的教練；頂部導覽新增「訓練師市場」按鈕。CLI(`cli/play.py`)在開局後、
進入每週迴圈前加一段互動式訓練師市場設定，`--auto` demo模式固定聘用市場第一
位並指定給第一匹馬，方便快速看流程。

補上21個測試(`cli/trainers.py` 純函式10個、`game.py` 整合9個、webapp路由2個)，

### 財務長週期驗證（加回訓練師薪水後重測）

`tools/financial_simulation.py` 改用 `--trainer-count N` 取代原本的布林開關：
開局優先聘用市場裡週薪最低的N名訓練師(模擬量入為出的理性玩家)，分散指定給
5匹馬，方便掃不同聘用規模對財務曲線的影響。用種子固定的20次(52週)/15次
(104週)試驗重跑：

| 聘用數量 | 52週破產 | 52週平均最終資金 | 104週破產 | 104週平均最終資金 |
|---|---|---|---|---|
| 0名(對照組，等同這個系統補回前) | 0/20 | 135,802 | 0/15 | 129,920 |
| 1名 | 0/20 | 120,555 | — | — |
| 2名(工具預設值) | 0/20 | 93,038 | 0/15 | 91,327(過程中最低點平均只剩37,473) |
| 3名 | 0/20 | 56,960(個別已轉負，只是52週內剛好沒觸發破產判定) | — | — |
| 4名(市場全聘) | 5/20 | 8,495 | 14/15 | -21,837 |

結論：訓練師系統確實把財務系統補出了原本設計意圖的緊張感，但風險曲線隨聘用
數量非線性上升——聘1~2名(對5匹馬的規模來說覆蓋大部分主力)是「有感但不致命」
的合理範圍，聘滿4名負擔過重、容易破產。

## 第6步：獸醫/傷病系統（`cli/injuries.py`、`cli/vets.py`）

依使用者要求，傷病種類與嚴重度參考現實賽馬常見的訓練/比賽耗損型傷病案例
（只取通俗名稱與大致恢復期/永久性後果的量級，不追求醫學精確，純供遊戲數值
設計參考，不是醫療資訊）：

| 嚴重度 | 案例(現實常見傷病) | 恢復期 | 永久減損 | 其他 |
|---|---|---|---|---|
| 輕傷 | 肌肉拉傷、副骨突起(夾骨)、輕微關節發炎 | 1~3週 | 無 | 4週內反覆發生會提高之後觸發中/重傷的機率 |
| 中傷 | 脛骨骨膜炎(buck shins，年輕馬常見)、韌帶扭傷、蹄葉炎初期 | 4~8週 | 依部位對應屬性-3% | — |
| 重傷 | 屈腱炎(肌腱部分斷裂)、懸韌帶損傷、疲勞性骨折 | 12~20週 | 依部位對應屬性-8% | 8%機率直接迫使退役 |

傷病風險分級(無/低/中/高)由健康+疲勞換算——狀態與健康.md原文是「疲勞+健康+
訓練強度+比賽頻率」四個因子，MVP簡化成健康+疲勞兩項，疲勞本身就是訓練/比賽
強度的累積結果，可視為代理指標。比賽週額外+2%觸發機率。

```
cli/
  injuries.py   # Injury dataclass、傷病判定/恢復的純函式
  vets.py       # Vet dataclass、獸醫市場生成
```

獸醫系統依 `docs/經營/員工系統.md`：跟訓練師不同，獸醫不分専長類型，統一用
單一技能等級(1~5)代表「恢復效率」(加速傷病倒數)、「傷病預防」(降低觸發機率)
兩項真正影響數值的能力(「健康評估精度」「配種前後檢查」跟訓練師的「潛力評估」
一樣先跳過，理由同見 `cli/vets.py` 模組docstring)。聘用要付一次性費用、之後
每週固定薪水(併入 `weekly_upkeep`)；一個獸醫最佳照顧5匹馬，6~8匹時效率下降，
9匹以上無法再指定。沒有指定獸醫時，傷病仍會依基礎速度自然恢復，只是沒有加速
跟預防加成，向下相容。

受傷或退役的馬 `train_horse()` 會直接拒絕(丟 `ValueError`)，也不能報名比賽
(`run_race()` 內建防呆過濾)。CLI(`cli/play.py`)跟網頁版都會在UI層先把受傷/
退役的馬排除在訓練/報名選項之外，只顯示目前狀態，避免玩家選了選項卻收到錯誤。
網頁版新增 `/vets` 頁面(比照 `/trainers`)，`dashboard.html` 新增「傷病」「獸醫」
兩欄，`race_entry.html` 對無法出賽的馬顯示原因取代報名表單。

`tools/financial_simulation.py` 補上 `--vet-count`(預設1)，比照
`--trainer-count` 的量入為出策略(優先聘週薪最低的幾位)；策略迴圈也加了
「受傷/退役就跳過訓練」的處理，避免直接撞上 `train_horse()` 的例外。

補上30個測試(`injuries.py` 純函式14個、`vets.py` 純函式2個、`game.py` 整合
12個、webapp路由2個)，測試總數59→90；並用 `--auto` 跑30週CLI demo，驗證完整
的「觸發傷病→養傷中無法訓練→倒數痊癒→恢復訓練/比賽」流程，以及獸醫加速恢復
都正常運作。

### 財務長週期驗證（加回獸醫薪水後重測）

試驗，結果跟先前一致(0~1/20破產量級)，確認設施系統本身不影響現有財務平衡——這點符合
預期，因為設施升級是玩家主動選擇的支出，不像訓練師/獸醫薪水是「聘了就每週固定要付」。

額外幫工具加了 `--facility-invest-threshold` 旗標，模擬「有閒錢就優先升級最便宜的
未滿級設施」的玩家策略。用閒錢門檻20,000測試發現一個值得注意的結果：因為每週只要資金
仍高於門檻就會再升一級、且升級費隨等級遞增(`8000×目前等級`)，這個「貪婪、每週持續
投資」策略在52週內把17/20次試驗都推向破產。這是財務驗證工具刻意做的壓力測試策略(比照
先前「全聘訓練師」壓力測試的做法)，**不是**遊戲本身的預設行為(預設完全不會自動投資
設施，需要玩家自己點按鈕)。但這也顯示：如果之後想在UI上引導玩家「有錢就儘量投資
設施」，目前的升級費用遞增曲線可能需要搭配某種節流機制(例如限制每季只能升一次、或把
費用曲線壓平)，否則容易從「投資」變成「陷阱」。是否需要調整交由使用者評估後決定。

## 第8步：訓練師/獸醫市場定期刷新

依使用者要求，訓練師/獸醫市場改成每 `MARKET_REFRESH_INTERVAL_WEEKS`(4)週自動刷新一次
未聘用的候選人清單(`cli/game.py` `refresh_markets_if_due()`)，讓玩家不會卡在開局那批
候選人裡，定期有新的員工可以選擇。刷新週期刻意跟比賽週(`is_race_week`，同樣是4週一輪)
對齊：開局第1週的候選人在第5週會換一批、第9週再換一批，以此類推。

只會替換「市場清單」(`state.trainer_market`/`state.vet_market`)，已經聘用的訓練師/獸醫
(`state.trainers`/`state.vets`)是完全獨立的清單，不受刷新影響——玩家不會因為市場刷新
就無緣無故被辭退人力、指定關係也不會被清掉。

連帶做了一個架構上的調整：訓練師/獸醫市場清單原本是 `webapp/app.py` 自己的全域變數
(`TRAINER_MARKET`/`VET_MARKET`)，開新局時才重新生成一次，這次搬進了 `GameState`
(`state.trainer_market`/`state.vet_market`)，讓市場狀態跟著遊戲進度一起走，而不是跟著
webapp行程的存活週期綁在一起。好處：(1) 市場才能真的「每4週」刷新，而不是只有開新局
才換一次；(2) 之後如果要做存檔/讀檔，市場清單會自動一起被存下來，不用另外處理。

webapp的 `/trainers`、`/vets` 頁面新增「下次刷新：第N週」的提示文字，讓玩家知道還要
等多久才會有新人選。補上9個測試(`game.py` 純函式邏輯5個：開局市場、未到期不刷新、
到期刷新、已聘用不受影響、同週重複呼叫不重複刷新；webapp路由層4個：頁面顯示刷新提示、
連續推進4週後市場確實換新、已聘用訓練師在市場刷新後仍保留指定關係)，測試總數115→123，
並用 webapp `test_client` 連續推進4週手動驗證市場候選人確實換新、已聘用的訓練師薪水/
指定關係都正常維持。

## 第9步：賽事分級擴充（11級）

「混合資格制」的一部分，先跳過，之後如果要做更真實的資格判斷可以回來補)。

向下相容是這次擴充的核心原則：原本3級的門檻(新馬賽0、地方一般賽58、GI80)、參賽數、
報名費、獎金表、名氣、比賽經驗成長基礎值全部維持原值不變，只在中間(0~58)、頂端

67／地方二級賽70／地方一級賽73／國際GIII76／國際GII78／國際GI80)。有一個命名調整：
`GI` 在 `RACE_GRADES` tuple裡改名為 `國際GI`(對齊doc原文的「國際賽事」分類)，程式跟
測試裡原本寫死的字串 `"GI"` 都已同步改成 `"國際GI"`。

`GRADE_FIELD_SIZE`(參賽數上限)保留原3級的假設值不變(新馬賽8、地方一般賽10、GI12)，

doc數字可以再單獨評估。

新增3個測試把關11級的完整性與一致性：每一級都要有理論上摸得到的門檻(用潛力上限檢查，
比照原本GI門檻可達性的測試精神)、6張對照表(門檻/報名費/對手強度/名氣/比賽經驗成長)的
資料都要隨分級單調不遞減、每一級的獎金名次數不超過參賽數上限。測試總數123→126，並用
`--auto` 跑40週CLI demo、webapp報名頁手動驗證11個分級選項都正常顯示與報名。

### 財務長週期驗證（11級化後重測，發現重要變化）

`tools/financial_simulation.py` 的簡化策略是「每4週報名可報的最高分級」。3級距時代這個
策略大部分時間停在地方一般賽(報名費2000)；11級化後同一個策略會沿著評級成長依序報名
表列賽 → 公開賽 → 三級賽 → ⋯ → GII(報名費一路爬到8000~9400)，途中任何一級名次不夠好
都要重付更高的報名費才能再試。

52週20次試驗(種子42)：平均最終資金從補回這個系統前的72,722跳到 **164,331**(最高一次
526,925)，但破產次數也從0~1/20升到 **2/20**。換個種子(7)、30次試驗，破產次數更到
**8/30(約27%)**，過程中最低點資金平均只剩29,537。

結論：11級化讓「持續往上衝最高分級」這個簡化策略的財務結果變得極端——上限更高，下限
也更容易碰到破產門檻。這**不是bug**，是新增中間級距讓玩家有更多「用報名費賭一把換更
高獎金」的選擇點，符合「賽事分級擴充」本身的設計意圖，但財務曲線的變異度明顯放大，且
下檔風險比先前任何一輪(訓練師/獸醫/設施)驗證都高。是否需要調整(例如財務驗證工具改成
更保守的「量入為出」報名策略、或重新檢視中間級距的報名費/獎金比例)交由使用者評估後
決定。

### 中間級距報名費/獎金比例調整（依使用者要求重新檢視）

診斷：原本11級化時，8個新增中間級距的「1st名獎金/報名費」比值只有 **5.56~13.83倍**，
明顯低於兩端既有的新馬賽/地方一般賽(6.0倍)、GI(20.0倍)——中間級距相對報名費「偏貴」，
尤其地方三級賽~國際GII這5站連續要繳5000~9400的報名費，任何一站名次不好就要用更貴的
報名費再試，是財務曲線變異度放大、破產率飆高的主要原因。

調整方式：只調降中間8個新增級距的 `GRADE_ENTRY_FEE`，讓比值從兩端的6.0倍平滑爬升到
GI的20.0倍(6.0 → 6.02 → 6.0 → 6.53 → 6.99 → 7.51 → 8.52 → 10.0 → 12.0 → 15.0 →
20.0)——刻意選擇「降低犯錯成本」而不是「調高獎金」，避免財務曲線的平均值/上限被進一步
推更高，只收斂下檔風險。新馬賽/地方一般賽/GI這3個原本3級時代就驗證過的既有報名費、
以及全部獎金表 (`GRADE_PRIZE_TABLE`)，完全沒有變動。

重新跑財務長週期驗證確認調整效果：52週20次試驗(種子42)破產次數從調整前的2/20降到
**1/20**，最高值從526,925收斂到337,115；換種子(7)、30次試驗，破產次數從27%(8/30)降到
**17%(5/30)**。再用5組不同種子(1~5)各20次試驗、共100次獨立試驗做整體驗證：平均最終
資金130,930、破產次數 **11/100(11%)**。

結論：調整後的破產率明顯比調整前收斂(從最壞情況27%降到約10~11%的區間)，但仍高於11級
化之前的基準值(0~1/20，約0~5%)——這是「持續往上衝最高分級」這個簡化策略本身的固有
特性(11個級距代表更多「用報名費賭一把」的選擇點，不是單靠報名費調整就能單獨消除的)，
這次調整已經達到「明顯改善但不強行壓回原本更保守的風險水準」的效果。是否要進一步調整
(例如財務驗證工具改成更保守的量入為出報名策略、或繼續調整中間級距費用)交由使用者
評估後決定。

## 第10步：賽事節奏改為每週一次（含出賽冷卻）

依使用者要求，賽事舉辦時間從原本每4週一次改成每週一次(`cli/game.py` `is_race_week()`
恆回傳`True`)，但馬匹在參加這週的比賽後，接下來2週不可再參賽，避免同一批馬無限連續
出賽。`Horse`(`cli/horses.py`)新增兩個欄位：`race_cooldown_weeks_remaining`(還在冷卻中
就是>0)、`raced_this_week`(這週是否剛出賽過，供傷病判定用，見下)。`can_race()`追加
`race_cooldown_weeks_remaining <= 0`這個條件。

冷卻週數的設定值刻意是`RACE_COOLDOWN_WEEKS`(2，`assumptions.py`新常數)+1=3，不是直接設
2：因為冷卻倒數(`apply_weekly_race_cooldown_recovery()`)是在出賽當週同一次結算交易裡
執行的，如果直接設2，當週結算內就會先扣掉1剩1，隔一週再扣到0，實際只擋到1週，不是
使用者要的「接下來2週不可參賽」。設3才會精準對應：出賽當週設3，同一次結算內先扣1剩2
(擋下第N+1週)，第N+1週結算再扣1剩1(擋下第N+2週)，第N+2週結算再扣1剩0，第N+3週才恢復
可報名——這是用逐週手動推演驗證過的，寫程式前先發現這個離線誤差，而不是靠測試踩到才
修正。新增`apply_weekly_race_cooldown_recovery()`：每週結算時把所有馬匹的冷卻週數倒數
1週(下限0)、並重置`raced_this_week`，webapp/CLI/財務驗證工具三個呼叫點都要記得呼叫，
不然冷卻永遠不會消。

連帶調整：`roll_weekly_injuries()`原本吃一個全域`is_racing_this_week`布林值(代表「整個
馬房這週是不是比賽週」)，但賽事變成每週開放後，大部分馬在大部分週其實沒有真的出賽(卡在
冷卻中)，全域旗標會誤判成「這週全部馬都在承受比賽週的額外傷病風險」。改成不吃參數，
內部逐匹馬讀`horse.raced_this_week`，只有真的出賽的那匹馬才吃比賽週的額外傷病風險加成，
沒出賽的馬(不管是休息還是冷卻中)不受影響。訓練迴圈裡的`roll_weekly_event()`(隨機事件
加成)刻意沒有比照修改，維持全域/馬房共用的旗標——理由是它代表整個馬房這週的活動氛圍，
而非個別馬匹承受的出賽負荷，跟傷病判定的性質不同，改成週週恆常生效是規則調整後很自然
的結果，不是bug。

UI同步更新：`webapp/templates/race_entry.html`對冷卻中的馬顯示「出賽冷卻中（還要N週
才能再出賽），本週無法報名」取代報名表單；`dashboard.html`「傷病」欄位新增冷卻中的
徽章；`cli/play.py`的`print_status()`也加了對應的狀態提示。

改寫2個假設「每4週才是比賽週」的舊測試(webapp路由層，原本的分支假設不再成立)，並新增
1個測試驗證馬匹出賽後接下來2週的報名頁確實不會出現它、第3週(冷卻結束)重新出現在報名
選項裡，測試總數126→127。用CLI `--auto`跑10週demo手動驗證：出賽後冷卻值3→2(當週結算
內)→1(下週)→0(再下週)，第3週後重新出現在可報名清單，跟設計預期完全一致。

### 財務長週期驗證（賽事變密後重測）

`tools/financial_simulation.py`的簡化策略本身完全不用改——`can_race()`已經把冷卻中的馬
排除，「有資格就報名可報的最高分級」這句話自然變成「沒在冷卻中、有資格就報」，程式面
零改動。但這個規則調整讓每匹馬出賽的頻率從「全馬房共用賽曆，最多每4週一次」變成「各自
獨立倒數，大約每3週一次」，出賽機會變密，出賽相關的報名費/獎金/名氣/傷病風險在整季裡
出現的次數也跟著變多，財務曲線需要重新驗證。

52週20次試驗(種子42)：平均最終資金**242,933**(對照調整前同種子130,930附近，明顯更高)、
最高521,835、破產次數1/20，跟調整前同一水準；換種子(7)、30次試驗，破產次數**2/30(約
6.7%)**，比調整前同種子的5/30(17%)更低。再用5組不同種子(1~5)各20次試驗、共100次獨立
試驗整體驗證：破產次數合計**4/100(4%)**，明顯低於調整前的11/100(11%)。

結論：賽事變密後，出賽相關的獎金/名氣收入機會也跟著變多，抵銷了報名費/傷病風險上升的
部分，整體財務曲線反而比調整前更寬鬆(上限更高、破產率更低)——這**不是bug**，是「機會
變多」跟「每次機會的風險」互相抵銷後的自然結果，也符合現實賽馬「出賽越密、賺錢機會越
多但養馬成本/傷病曝險也越高」的直覺，只是在這個簡化策略下前者的效果更明顯。是否需要
進一步調整(例如財務驗證工具改成更保守的策略、或調高部分支出項目，讓緊張感回到11級化
剛推出時的水準)交由使用者評估後決定。

### 中間級距報名費/獎金比例改回原值（依使用者要求撤回先前的調整）

依使用者要求，把「中間級距報名費/獎金比例調整」那一輪(見上方)對`GRADE_ENTRY_FEE`的
調降撤回，改回11級化剛推出時的原始數值：未勝利賽900(原830)、地方表列賽2800(原2450)、
地方公開賽3800(原3150)、地方三級賽5000(原4250)、地方二級賽6500(原5400)、地方一級賽
8000(原6500)、國際GIII8800(原7500)、國際GII9400(原8650)。兩端3個原本3級時代就驗證過
的既有數字(新馬賽/地方一般賽/GI)、以及全部獎金表(`GRADE_PRIZE_TABLE`)從頭到尾都沒
變動過，這次撤回也一樣沒動。程式面沒有其他改動，127個測試不受影響全數通過。

重新跑財務長週期驗證(此時賽事已經是每週一次+出賽冷卻2週的規則，見上方「第10步」)：
52週20次試驗(種子42)：平均最終資金184,698(比調整後的242,933低，但比從未調整過的
未知基準更接近報名費調整前的財務緊張感)、破產次數**3/20**；換種子(7)、30次試驗，破產
次數**5/30(約16.7%)**。再用5組不同種子(1~5)各20次試驗、共100次獨立試驗整體驗證：破產
次數合計**10/100(10%)**，比撤回前(調整後、賽事每週化)的4/100(4%)明顯升高，回到接近
「11級化剛推出+報名費未調整」那一輪的11/100(11%)水準。結論：撤回報名費調整後，財務
緊張感確實回升，符合預期——中間級距的報名費/獎金比例現在維持11級化剛推出時的原始設計，
之後如果要再次調整交由使用者評估後決定。

## 第11步：馬匹年齡系統 + 新馬賽/未勝利賽生涯資格制

依使用者要求，新增馬匹年齡系統(對應GDD 3.6「成長與老化」)，並用年齡+生涯出賽紀錄取代
純評級門檻做為新馬賽/未勝利賽/一般賽事的資格判定：

- **新馬賽**：只有`MAIDEN_RACE_AGE`(2)歲、且生涯從未出賽過(`career_starts == 0`)的馬才能
  報名。出賽過一次(不論分級、不論名次)就永久不能再報名新馬賽——即使那次就是新馬賽本身。
- **未勝利賽**：已經出賽過(`career_starts >= 1`，代表已經跑過新馬賽)、但還沒「畢業」
  (`not graduated`，代表新馬賽沒贏)的馬才能報名。
- **地方一般賽以上(一般賽事)**：只有已經「畢業」(`graduated`，代表贏過新馬賽或未勝利賽)
  的馬才能報名。

「畢業」規則：在新馬賽或未勝利賽奪得第1名的當下(`cli/game.py` `run_race()`)把
`horse.graduated`設為`True`，之後永久生效——不會因為之後戰績不好被取消，但畢業後也不能
再回頭報名新馬賽/未勝利賽，比照真實賽馬「條件戰」一去不回頭的精神。這套生涯資格制是
「疊加」在原本的評級門檻(`GRADE_ELIGIBILITY_THRESHOLD`)之上，兩者都要滿足才能報名——
既有的評級門檻/報名費/獎金表/名氣/比賽經驗成長基礎值完全沒有變動，只是在新馬賽/未勝利賽/
一般賽事這3層之間多了一道生涯進程的關卡。

`Horse`(`cli/horses.py`)新增3個欄位：`age`(預設2歲，對應`STARTER_HORSE_AGE`)、
`career_starts`(生涯出賽次數，`run_race()`每次出賽都會+1，不分名次)、`graduated`(是否已
畢業)。年齡增長由新函式`apply_weekly_age_progression()`負責：MVP簡化把「一年」直接對應
`WEEKS_PER_YEAR`(52)個遊戲週，開局5匹測試馬視為同一批「出生」，滿52週整批一起長一歲，
不用替每匹馬分別追蹤生日；退役馬不再計算年齡增長。webapp/CLI/財務驗證工具三個呼叫點都
已同步加上這個函式的呼叫(比照`apply_weekly_race_cooldown_recovery`的呼叫模式)。

刻意縮小的範圍：這次只做「年齡數字本身+新馬賽資格判定」，不做GDD 3.6完整的四種成長曲線
類型(早熟/一般/晚成/持久型)與上升期/巔峰期/停滯期/衰退期倍率換算——`FIXED_AGE_STAGE_
MULTIPLIER`仍維持原本固定的1.15不變。理由：完整成長曲線是獨立的大工程，且會直接牽動
既有已驗證多輪的訓練/財務平衡，這次的請求範圍是「年齡系統+新馬賽/未勝利賽資格制」，沒有
要求連動訓練成長曲線，所以先不做，之後如果要延伸成長階段影響訓練倍率交由使用者評估後
決定再單獨處理。

最終補救規則(2026/8/25)：一匹馬如果在年齡結算後超過`MAIDEN_RACE_AGE`仍從未出賽，
會立即自動退役並取消訓練師/獸醫指派；玩家之後可在繁殖頁面或CLI選擇登記為種馬/
繁殖母馬，或維持一般退役。超齡馬不能直接從未勝利賽出道。

UI同步更新：`dashboard.html`、`race_entry.html`新增「年齡」欄位；`race_entry.html`對
「能出賽但目前沒有任何符合資格分級」的馬(例如剛輸掉新馬賽、評級還不到未勝利賽門檻)，
顯示具體原因而不是空的下拉選單，避免玩家誤以為是bug。`cli/play.py`的`print_status()`
也加了年齡顯示。

新增12個測試(`tests/test_game.py`)覆蓋：開局測試馬的初始年齡/生涯狀態、出賽過的馬不能
再報新馬賽、超齡未出賽的馬不能報新馬賽、輸掉新馬賽的馬能報未勝利賽但不能報一般賽事、
畢業的馬能報一般賽事但不能回頭報新馬賽/未勝利賽、`run_race()`
確實會累加生涯出賽次數、用壓倒性屬性(全100 vs NPC中樞45)確保奪冠來驗證「奪冠即畢業」
(新馬賽、未勝利賽各驗證一次，各連續跑15次確認不會因為隨機波動而翻盤)、輸掉比賽只累加
出賽次數不畢業、年齡只在滿52週的那一週才增長、退役馬不計入年齡增長，測試總數127→139。
另外用CLI`--auto`實測20週：「全能強馬」第1週新馬賽奪冠直接畢業，第4週就跳去報名國際GIII
(報名費8800、獎金76500)，之後全部集中在地方公開賽~一級賽之間，完全沒有再回頭報名新馬賽
或未勝利賽，跟設計預期完全一致；也用55週驗證第52週結算後全部5匹測試馬正確從2歲長到3歲。

### 財務長週期驗證（生涯資格制上線後重測）

策略本身完全不用改(`grades[-1]`挑最高分級的邏輯，會自然吃到新的`eligible_grades()`結果)，
但生涯資格制讓沒能一次奪冠的馬，得先在未勝利賽(報名費900、獎金遠低於中高分級)裡繼續繳費
才能畢業，等於延後了牠們摸到高獎金分級的時間，財務曲線需要重新驗證。

52週20次試驗(種子42)：平均最終資金210,286、破產次數**2/20**；換種子(7)、30次試驗，破產
次數**7/30(約23.3%)**；5組種子(1~5)各20次試驗、共100次獨立試驗整體驗證：破產次數合計
**13/100(13%)**，比生涯資格制上線前(報名費改回原值後)的10/100(10%)略高。結論：生涯資格
制讓「評級已經夠高但運氣不好沒能在新馬賽奪冠」的馬，得在低報名費/低獎金的未勝利賽裡多繳
幾次報名費才能畢業，財務下檔風險小幅上升，符合預期方向、幅度不算劇烈(10%→13%)。是否需要
調整(例如財務驗證工具改成更保守的策略，或未勝利賽的報名費/獎金比例)交由使用者評估後決定。

## 第13步：繁殖/遺傳系統（簡化版）

依使用者要求新增繁殖/遺傳系統(GDD第9節「血統與繁殖系統」/「遺傳系統」，MVP範圍.md
原本列在「先跳過」清單)。開工前先跟使用者確認3個範圍問題：

1. **配種機制深度**：GDD原文有自然交配/人工授精雙軌、21~22天發情週期、配種前後獸醫
   檢查等細節流程。使用者選擇**簡化版**：只做「配種」單一動作，扣固定成本
   (`BREEDING_COST`=2000)、判定成功率(`BREEDING_SUCCESS_CHANCE`=80%)，成功後進入
   固定產駒期(`GESTATION_WEEKS`=48週，對應「約11個月」)倒數，配種嘗試之間有固定冷卻
   (`BREEDING_ATTEMPT_COOLDOWN_WEEKS`=8週)取代真正的發情週期倒數。
2. **繁殖資格**：GDD原文「退役馬轉型成為繁殖馬」+ 3~12歲限制。使用者選擇**先退役才能
   繁殖**(照GDD原文精神)，不開放現役中的馬直接配種——這也讓這次工作補上一個既有缺口：
   MVP之前完全沒有「玩家主動讓馬退役」的管道(`retire_horse()`)，只有重傷會自動觸發退役。
3. **幼駒屬性生成**：使用者選擇**父母屬性平均+隨機浮動+潛力隨機制**：11項屬性=父母
   平均±常態分布浮動(`BREEDING_STAT_SPREAD`=8)，整體潛力=父母潛力平均為中樞的常態
   分布浮動(`BREEDING_POTENTIAL_SPREAD`=6，不裁切上限，可能突破父母)。不做特性/性格/
   適性/血統相性遺傳(GDD雖列了但這些是次要遺傳細節，這次範圍刻意不做)。

新增`cli/breeding.py`：`generate_foal()`依父母資料生成新出生幼駒(0歲)，`_is_inbred()`
用1代血統(`Horse.sire_name`/`dam_name`)判斷近親——只抓得到「親子配」「同父/同母的
手足配」這兩種情況，抓不到隔代或更遠親緣的近親繁殖，是刻意接受的簡化限制。近親繁殖時
潛力中樞打8折(`BREEDING_INBREEDING_POTENTIAL_PENALTY_PCT`=0.2)，並有30%機率
(`BREEDING_INBREEDING_HEALTH_ISSUE_CHANCE`)觸發健康屬性打8折的「遺傳疾病」(遺傳
系統.md「限制子代潛力上限與健康狀況」)。

懷孕當下拍照存證的種馬屬性/潛力快照`pregnant_sire_stats`/`pregnant_sire_potential_cap`
+近親旗標`pregnant_inbred`)、配種冷卻(`breeding_cooldown_weeks_remaining`)。快照
設計是為了避免種馬在懷孕期間被賣掉/屬性被訓練改變時，幼駒出生當下算不出來或算錯。
開局5匹測試馬、`horse_market.py`市場馬都補上性別，沒有血統紀錄的馬不會被誤判近親。

新增`Horse.can_train()`：馬匹成長.md「1歲可以開始訓練」，配合幼駒從0歲出生的新狀態
新增這個門檻(`MIN_TRAINING_AGE`=1)，`train_horse()`未滿1歲會丟例外，webapp/cli的
訓練迴圈也都補上這個檢查。開局測試馬/市場馬固定2歲起跳，不受影響，向下相容。

(互動模式每週詢問、`--auto`demo模式完全跳過，比照`handle_horse_market`的精神)。

補上30個測試(`tests/test_breeding.py`26個 + `tests/test_webapp.py`4個)，測試總數
152→182，並用`--auto`跑60週CLI demo、互動模式手動跑過一輪退役→登記→配種→生產的

只補上`apply_weekly_pregnancy_progression()`的呼叫維持三處入口一致。

**刻意縮小範圍(先跳過)**：種馬市場/繁殖母馬市場/幼駒市場(GDD第8節市場剩下的3類，

## 第15步：成長曲線類型與階段轉換（`cli/growth.py`）

- **`Horse.growth_curve`欄位**：新增的成長曲線類型欄位（早熟/一般/晚成/持久型之一），

  curve()`獨立隨機決定，不參考父母或任何虛構血統。

  約減緩27%，怎麼升級都不會讓倍率變成0)，「獸醫照護」「降低比賽/訓練強度」這2個
  管道先跳過，之後有需要再補（目前獸醫的「恢復效率」專長只影響傷病恢復，訓練/比賽

  設計，因為`breed()`會拍照存證種馬當下的屬性快照，讓「越老的種馬素質越差」自然

## 第16步：特性/性格系統（`cli/traits.py`）

依使用者要求，把MVP範圍.md「先跳過」清單裡的特性/性格系統補上。開工前先確認過2個
範圍問題：

1. **特性取得方式**：馬匹系統.md 9種特性各自標記「天生」「訓練」「天生/訓練」其中
   之一。使用者選擇**簡化版**：不分天生/訓練，9種特性統一在馬匹出生/生成當下隨機
   分配(0~2個)，包含文件寫「訓練」限定的領放穩定/抗壓也一併開放進天生隨機池——避免
   這2個特性因為沒有做「訓練習得」機制而永遠不會出現。之後如果要做「透過特定訓練
   機率習得」可以再加，不影響`Horse.traits`的資料結構。
2. **個性(性格)**：使用者選擇**純風味**，不掛任何數值效果——比賽公式.md、培育系統.md
   都沒有引用性格，文件本身沒有給具體公式。這裡只做顯示欄位+簡化版遺傳規則，不影響
   任何訓練/比賽數值。

- **新模組`cli/traits.py`**：`TRAIT_DEFS`定義9種特性各自的正面/負面、觸發條件敘述、
  可遺傳性(是/否/可能)；`random_traits()`依`TRAIT_COUNT_WEIGHTS`(0個45%/1個40%/2個
  15%，doc沒給具體數字的MVP假設值)隨機決定馬匹出生/生成時的特性清單；`trait_triggers()`
  依跑法/賽事分級判定這場比賽會不會觸發；`race_trait_bonus_pct()`把「這場比賽觸發的
  特性」加總成單一全場次百分比。
- **維持引擎既有算法不變**：比賽公式.md文字描述特性是「每個特性觸發時對所屬階段表現」
  修正，但數值平衡試算.xlsx「比賽模擬」分頁本身把特性算成單一全場次百分比套進
  `engine/race.py external_multiplier()`(套用在全部六階段，不是逐階段各自套用)，
  既有22個核心引擎測試都是照這個公式比對到1e-9精度——這裡刻意不改`engine/race.py`，
  只在`cli/game.py _horse_to_race_input()`用`traits.race_trait_bonus_pct()`算出
  每匹馬這場比賽的加總百分比，取代原本寫死的`trait_bonus_pct=0.0`。
- **`Horse.traits`/`Horse.personality`欄位**：新增，開局5匹測試馬給固定指派(全能
  強馬=快速起步+末段爆發/好勝、速度型快馬=領放穩定+快速起步/喜歡領跑——牠跑法正好是
  「逃」吃得到領放穩定的觸發條件、耐力追込馬=末段爆發/冷靜、平衡中庸馬=無特性(平凡
  基準馬對照組)/慢熱、潛力新星=容易緊張/膽小)。
- **不遺傳 vs 部分遺傳**：跟成長曲線(完全不遺傳)相反，遺傳系統.md「特性遺傳」「性格
  遺傳」都是「部分會遺傳」，所以現役馬/幼駒/種馬/繁殖母馬市場(`cli/horse_market.py`4
  個生成函式)一律呼叫`random_traits()`/`random_personality()`獨立隨機(市場馬沒有
  真實血統可以遺傳)，但配種生出的幼駒(`cli/breeding.py generate_foal()`)改呼叫

  「可能」15%、「否」(領放穩定/抗壓)完全不遺傳，沒遺傳滿上限的部分保留30%機率額外
  隨機長出新特性；性格則是父母任一方帶有`PERSONALITY_HERITABLE`(冷靜/暴躁)時30%機率

  `breed()`當下記錄、`apply_weekly_pregnancy_progression()`生產時讀出。
- **暫時「沉睡」的特性**：重馬場高手(觸發條件：重馬場)、海外適應(觸發條件：海外賽事)

- **UI顯示**：CLI的`print_status()`補上「特性:.../個性:...」；webapp的

   時機/馬匹能力曲線跟預期落差太大，這幾個常數是優先檢視對象(見`cli/growth.py`
   模組docstring)。
5. 特性系統目前是「不分天生/訓練，全部天生隨機」的簡化版，也還沒開放玩家透過訓練
   主動習得特性；性格是純風味欄位，之後如果要做NPC馬主決策或想讓性格影響數值，
   這兩塊都是現成的擴充點(見上方「第16步」)。重馬場高手/海外適應這2個特性要等場地
   狀況變化/海外賽事系統之後補上才會真的觸發。特性效果強度(5%~8%)、各特性的觸發
   機率權重(TRAIT_COUNT_WEIGHTS)、遺傳機率(TRAIT_INHERIT_CHANCE)也都是doc沒給精確
   數字時的MVP假設值，優先檢視對象見`cli/traits.py`模組docstring。
